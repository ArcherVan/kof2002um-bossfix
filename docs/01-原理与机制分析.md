# 原理与机制分析

> 本文是技术细节文档。只想用工具的话看 [README](../README.md)；想理解"为什么这么写"或为自己的版本重新对位，看这篇。

---

## 0. 结论摘要

| 项 | 结论 |
|---|---|
| 伤害落地指令 | `0x620902`：`sub word ptr [eax+0x138], dx`，`eax` = 受击方 |
| HP 字段 | 角色对象 `+0x138`（int16）；累计伤害在 `+0x1F4` |
| 伤害后处理链 | `0x628200`–`0x628264`，含 ×0.5 与 ×0.75 两档 |
| ×0.5 实现 | `0x627E40`：`shr word ptr [$v0槽], 1` |
| ×0.75 实现 | `0x627E60`：`ax = ax/2 + ax/4` |
| 两档关系 | **if/else 互斥**，不会连乘 |
| 触发位 | `+0x11D` bit0（×0.5）、`+0x0E6` bit6（×0.75） |
| 秒杀哨兵 | 伤害 `0xFF` → 改写为 `0x7FFF` |
| 这条链的真实身份 | **多段命中衰减**（作用于受击方），与 BOSS 无关 |
| 玩家选 BOSS 的攻击力下降 | **仍未定位**（倍率与位置均未知） |
| 本项目方案 | 在落地指令挂钩，按可调倍率放大玩家输出 |

## 1. 运行时环境的三个前提

### 1.1 `.text` 在磁盘上加密

实测（`KingOfFighters2002UM.exe`，4,748,304 字节）：

| 指标 | 磁盘 | 内存 |
|---|---|---|
| `.text` 熵 | 7.9999 | 6.2166 |
| 可写性 | — | RWX |

- 解密只覆盖到 `VirtualSize`（尾部 1346 字节零填充，磁盘值 == 明文）；
- 取 4000 组"内存中完全相同的 16 字节明文块"，对应磁盘密文 4000 组全不相同 → 不是 ECB；但无法证伪 CBC/流密码。

**结论**：磁盘上改一个字节等于改密文，游戏会起不来。所有改动只能在进程内对已解密代码进行。

### 1.2 这是"重编译的 MIPS"

Code Mystics 的 FOCAL 框架把 PS2 的 MIPS 代码静态重编译为 x86。后果是：

- MIPS 寄存器**没有**落到真实 x86 寄存器，而是溢出到固定全局槽；
- 条件判断结果先写进"结果槽"，随后用 `test`/`je` 取用；
- 函数调用先把 `$ra` 槽写成常量（PS2 返回地址），再用普通 `call`；
- 栈是软件模拟的。

寄存器槽映射（后续所有分析都建立在它之上）：

| 槽地址 | 含义 | 证据 |
|---|---|---|
| `0x21E3440` | `$v0`（返回值 / 伤害值） | 落地前 `mov dx, word [0x21E3440]` |
| `0x21E3400` | `$a0` | 调用前装载参数 |
| `0x21E3420` | `$a1` | 同上 |
| `0x21E3408` | 条件判断结果槽 | 每次比较后 `mov [0x21E3408], eax` |
| `0x21E3448` | `$ra` / 临时指针 | `mov [0x21E3448], 0x7164F0` |
| `0x21E3450` | 软件栈指针 | `sub eax,2 / mov [eax],cx` |

这解释了为什么"搜 0.5 浮点常量"全部落空：折半的形态是 `shr word [0x21E3440], 1`，作用在一个"看起来像全局变量"的槽上，而这个槽全代码有上千处使用，无法用"谁写了 0.5"来定位。

### 1.3 角色对象地址固定

匹配初始化代码把两个对象地址直接写死：

```
[0x21E3414] = 0x167D360      ; P1 角色对象
[0x21E3414] = 0x167D580      ; P2 角色对象
```

所以"受击方是谁"不需要额外推断，比较 `eax` 与这两个常量即可。

## 2. 伤害链路

落地函数 `0x6207E0`，核心片段：

```asm
0x6208D6  movzx eax, word ptr [0x21E3440]   ; eax = 伤害值
0x6208DD  push  eax
0x6208DE  call  0x675270                    ; 伤害数字弹出 / 特效
0x6208E3  mov   eax, [0x21E3414]            ; 受击方对象
0x6208E8  mov   cx,  word ptr [0x21E3440]
0x6208EF  add   word ptr [eax+0x1F4], cx    ; 累计伤害（血条残影 / 连段统计）
0x6208FB  mov   dx,  word ptr [0x21E3440]
0x620902  sub   word ptr [eax+0x138], dx    ; ★ HP -= 伤害
0x62090F  movsx eax, word ptr [ecx+0x138]
0x620919  mov   [0x21E3408], eax
0x62091E  test  eax, eax
0x620920  jl    0x620948                    ; 小于 0 → 归零（KO 夹取）
```

要点：

- **`eax` 是受击方**，这是钩子能做"只放大玩家输出"判断的基础；
- `+0x1F4` 的累计伤害用的是折半**之后**的值，所以补偿会连带影响血条残影与连段统计；
- 同一套「写入 + 夹取」在 `0x4DBB0F`、`0x620902`、`0x63EFDA` 重复出现（普通命中 / 削血 / 投技等不同路径），但钩子只需挂 `0x620902`——所有路径最终都走这里。

## 3. 伤害后处理链

伤害落地之前经过这一段：

```asm
0x628200  mov   cx, word ptr [0x21E3440]
0x628207  movsx eax, cx
0x628211  jne   0x628218
0x628213  jmp   0x627930                    ; 伤害为 0 → 无伤害分支

0x628218  cmp   byte ptr [0x2211B90], 0     ; 数据版本选择（P_DATAA / P_DATAN）
0x62821F  jne   0x628237
0x628221  mov   eax, 0xFF
0x628226  cmp   cx, ax
0x628229  jne   0x628237
0x62822B  mov   ecx, 0x7FFF
0x628230  mov   word ptr [0x21E3440], cx    ; 伤害==0xFF → 0x7FFF（秒杀哨兵）

0x628237  mov   eax, [0x21E3414]            ; 当前对象
0x62823C  movsx edx, byte ptr [eax+0x11D]
0x628243  and   edx, 1
0x628246  mov   [0x21E3408], edx
0x62824C  je    0x628253
0x62824E  jmp   0x627E40                    ; ★ ×0.5

0x628253  movsx eax, byte ptr [eax+0x0E6]
0x62825A  and   eax, 0x40
0x62825D  mov   [0x21E3408], eax
0x628262  je    0x628213
0x628264  jmp   0x627E60                    ; ★ ×0.75
```

两档的实现本体：

```asm
0x627E40  66 D1 2D 40 34 1E 02   shr  word ptr [0x21E3440], 1
0x627E60  66 A1 40 34 1E 02      mov  ax, word ptr [0x21E3440]
0x627E66  D1 E8                  shr  ax, 1
0x627E69  66 89 C1               mov  cx, ax
0x627E6C  D1 E9                  shr  cx, 1
0x627E6F  01 C8                  add  ax, cx          ; ax = ax/2 + ax/4
0x627E72  66 A3 40 34 1E 02      mov  word ptr [0x21E3440], ax
```

关键结构：

- `0x62824C je 0x628253` —— bit0 命中时**直接跳走**，不再检查 `0x40`。所以是 **if/else 互斥**，最坏 ×0.5 或 ×0.75，不存在 ×0.375。
- `0x628221` 的 `0xFF → 0x7FFF` 是**秒杀哨兵**：某些招式脚本用 `0xFF` 表示"必死"，引擎换成 32767 以确保打死。它和折半共用 `[0x2211B90]==0` 这个前置门控。

### 3.1 标志位由谁置位 / 清除

×0.5 标志（`+0x11D` bit0）的**唯一置位点**：

```asm
0x60D9EF  mov  eax, [eax + 0xB8]            ; 角色子对象
0x60D9F8  cmp  byte ptr [0x2211B90], 0
0x60DA04  jne  0x60DA1C
0x60DA06  80 88 1D 01 00 00 01  or byte ptr [eax+0x11D], 1   ★ 打开 ×0.5
0x60DA1C  80 88 E6 00 00 00 01  or byte ptr [eax+0x0E6], 1   （另一套数据时用）
```

`0x60D9E0` 本身不是一个普通函数，而是一个**脚本 VM 命令处理程序**：

- 函数头 `push 0x157A; call 0x45D0A0` 是该重编译器的"压返回地址 + 跳板"调用约定（软件栈调用，不是 x86 `call`）；
- 在 `.data`（运行时基址 `0x75A000`）能找到它的分发表项，8 字节一项 `(处理程序, 命令号)`：

```
0x78A9C0  0060D860  00005AC0
0x78A9C8  0060D8C0  00005ABF
...
0x78AA00  0060D9E0  00005BC9      ← ★ 置 ×0.5 的那条命令
```

也就是说，**"给伤害打对折"是角色脚本字节码里的一条命令（`0x5BC9`）**，由招式/状态脚本主动调用。这解释了为什么在 `0x60C000`–`0x60E000` 整段里翻不到"角色 ID 是否 BOSS"的比较——判定在上层脚本里，不在引擎里。

清除点是一个干净的独立函数 `0x63EB00`：

```asm
0x63EB10  and byte ptr [eax+0x0E6], 0xBF    ; 清 ×0.75
0x63EB1C  and byte ptr [eax+0x11D], 0xFE    ; 清 ×0.5
0x63EB23  ret
```

调用者是一批状态动作小函数（`0x641350`、`0x641380`、`0x641D2D`、`0x643A59` 等）。

## 4. 一次实测推翻了上面的结论

### 4.1 最初的判断

看到"全局唯一的折半置位点 + 与秒杀逻辑写在同一段"后，判断这是"玩家选 BOSS 时攻击力被削"，于是打了 4 个 NOP 补丁：

| 组 | VA | 原字节 | 补丁 |
|---|---|---|---|
| halve | `0x60DA06` | `80 88 1D 01 00 00 01` | `90`×7 |
| halve | `0x62824E` | `E9 ED FB FF FF` | `90`×5 |
| scale75 | `0x60DA1C` | `80 88 E6 00 00 00 01` | `90`×7 |
| scale75 | `0x628264` | `E9 F7 FB FF FF` | `90`×5 |

实机验证：4 个位点字节与静态分析逐字节吻合，游戏稳定运行 97 秒演示循环。看起来一切正常。

### 4.2 反馈：毫无变化

用户实测后的反馈是"伤害完全没有任何变化"。

于是换思路：不再猜，直接在落地指令 `0x620902` 挂钩，把 `(受击方, 伤害, [0x21E3414])` 三元组逐次打出来。

### 4.3 数据

共 279 次命中：

| 观测项 | 结果 |
|---|---|
| `[0x21E3414]` 与受击方的关系 | **279/279 全部等于受击方** |
| 与攻击方的关系 | 0 次 |
| 伤害序列 | `11 → 5 → 2 → 1 → 1 → 1`（命中数越多越低，最低 1） |
| 普通角色对战 | 同样出现该递减 |

### 4.4 结论

`0x628200` 那条链处理的是**受击方吃到的伤害**，实现的是 2002UM 的**多段命中衰减**：连段每多打一下，伤害按 1/2、3/4 两档依次下调，最低压到 1。

那 4 个 NOP 补丁的实际效果是"**关闭连段伤害衰减**"，与 BOSS 无关，还会让连段伤害偏高、破坏平衡。**已全部废弃并从工具中移除。**

### 4.5 修正后的机制图

| 机制 | 作用对象 | 状态 |
|---|---|---|
| 多段命中衰减（×0.5 / ×0.75） | 受击方 | 已定位，**未修改**（正常机制） |
| CPU 用 BOSS 时的受击减伤 | CPU 侧 | 已观察，未修改 |
| **玩家选 BOSS 时的攻击力下降** | 攻击方 | **倍率与位置未定位** |

第三条发生在伤害**计算**阶段（在落地之前的上游），不在本链中。已尝试并排除的方向见第 7 节。

## 5. 本项目的补偿实现

既然上游没定位，就在下游把伤害乘回来。

### 5.1 挂载点与 cave 布局

在 `0x620902` 写入 `jmp cave`（补齐 2 字节 NOP），cave 内布局：

| 偏移 | 内容 |
|---|---|
| `+0x000` | 机器码 |
| `+0x400` | ring A：64 × dword，受击方地址 |
| `+0x500` | ring D：64 × dword，伤害值 |
| `+0x600` | 计数器 |
| `+0x700` | ring B：64 × dword，`[0x21E3414]` |
| `+0x800` | 版本标记 `HKD3` |
| `+0x810` | 补偿开关（dword，0=关） |
| `+0x814` | 倍率（dword，256 = ×1.0） |

### 5.2 执行流程

```asm
pushfd / push ecx / push edx
ecx = [ctr] & 63                  ; 防越界
ring[ecx] = eax / edx / [objslot]
inc [ctr]

cmp dword [flag], 0               ; 开关
je  done
cmp eax, P2                       ; 受击方 == 2P 对象？（即玩家在攻击）
jne done
movzx ecx, word [esp]             ; 取栈上保存的 dx
imul  ecx, [factor]
shr   ecx, 8                      ; 8 位定点还原
mov   [esp], ecx                  ; 覆写 dx

done:
pop edx / pop ecx / popfd
sub word ptr [eax+0x138], dx      ; 原指令
jmp 0x620909
```

设计取舍：

- **定点而非浮点**：`factor/256` 实现，避免 `fild`/`fmul` 污染 x87 状态与标志位；
- **开关与倍率放在 cave 内**：切换只需写两个 dword，不必重装钩子；
- **保留原指令在 cave 末尾**：跳回时现场与未挂钩时完全一致，不影响后续 `movsx` / `test` / `jl` 的夹取逻辑；
- **环形缓冲**：无锁、不阻塞游戏线程，只做诊断，64 条足够看一次连段。

### 5.3 自愈式安装

`install` 的判断顺序：

```
读 0x620902
├─ 等于原指令 → 全新安装
├─ 首字节 0xE9 → 顺着 jmp 找 cave
│   ├─ 机器码特征 + 标记 HKD3 对得上 → 认领（幂等）
│   ├─ 特征对得上但标记不同 → 旧版 → 还原后重装
│   └─ 读不到目标内存 → 失效跳转 → 还原后重装
└─ 其他字节 → 报错退出（拒绝盲改）
```

这套逻辑是踩坑换来的：早期版本把状态存在 `hookdmg.json` 里，文件丢失时会把自家的 `jmp` 误判成"字节不符"，结果在游戏里留下一条指向已释放内存的跳转，一受伤就崩溃。现在状态完全由内存自证，不再依赖外部文件。

### 5.4 为什么不做"自动识别 BOSS"

试过的方向都不成立：

- 引擎里没有"角色是否 BOSS"的字段（`+0x72` 与 `0x9E` 比较过，是攻击/动作 ID 一类）；
- `0x420900` 是菜单层的"随机/选 BOSS"判定，不在伤害路径；
- `+0x11D` 是**按招式临时置位**的状态字节，不是角色固有属性（实测双方同时为 0）。

所以只能退化为"只对 1P 攻击生效 + 手动开关"。

## 6. 为其他版本重新对位

换 repack / 换游戏版本后，若 `kof.cmd doctor` 报 `钩子点字节不符`，按下面顺序做：

1. **确认是不是同一个二进制**

   ```bat
   certutil -hashfile "路径\KingOfFighters2002UM.exe" MD5
   ```

   与 `e7a78eb4f724f65f12084bfc6e12420b` 一致 → 直接用默认配置；不一致 → 继续。

2. **找落地指令**

   搜索特征字节 `66 29 90 38 01 00 00`（`sub word ptr [eax+0x138], dx`）。若 `0x138` 变了，按 `66 29 ?? <偏移> 00 00` 放宽搜索，再用"HP 实际变化"确认候选。

3. **找 1P/2P 对象地址**

   在匹配初始化代码里搜 `mov dword ptr [0x21E3414], imm32`，会出现两条相邻写入，分别对应 P1/P2。也可以用 `kof.cmd status` 读血量，确认对象是否随战局变化。

4. **写入 `config.json` 并验证**

   ```bat
   kof.cmd config      # 确认地址已生效
   kof.cmd doctor      # 确认字节匹配
   kof.cmd install
   kof.cmd watch 60    # 打几下，看伤害是否按倍率放大
   ```

5. **提交指纹**

   把 `doctor` 输出、EXE 大小与 MD5 提 PR 到 `docs/03-兼容性与环境适配.md` 的矩阵里，方便后来人。

## 7. 已排除的假线索

记录在此，避免重复劳动：

- `double 0.5`（`0x6FF680`）→ 精灵插值中点，与伤害无关；
- `imul ×100` 共 8 处 → 百分比显示、`mm:ss` 计时格式化；
- `imul ×50`、Q12 `0x800`、全代码 `sar/shr 0xC` → 与伤害无关；
- `0x638B0E` 的 `shr dx,1` → 精灵旋转角度折半（写 `+0x164`）；
- `0x4D775C` / `0x6233B7` 一带对 `+0xD2/0xD4/0xD6` 等的 `sub` → 三轴坐标/速度积分；
- `0x420900` → 菜单"随机/选 BOSS"判定；
- `0x2D1BC4E/4F` → 装载器用的"当前加载 ID"，不参与对战；
- `cslst.dat` → 队伍选择表；`base/game.bin`、`boss.bin` → 脚本/指针表；
- `0x2D1BE00` 的 40×30 word 表 → 声音通道优先级；
- `Data\game\fight\p_dataa.bin` / `p_datan.bin` → 两套平衡数据，已确认头部结构（解析器 `0x443860`），但**没有找到"BOSS 段 ≈ 普通段一半"的参数表**。
